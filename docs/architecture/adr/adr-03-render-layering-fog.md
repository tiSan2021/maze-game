# ADR-03 · 渲染分层与迷雾动态更新（双路径）

- **状态**：Accepted（含降级预案）
- **主题**：三层离屏（L0/L1/L2）+ tile 预渲染 + L1 增量更新；关 1–8 回退全烘焙、关 9+ 走三层增量；性能预算 **< 8ms** 的三必做前置（tile 预渲染 / R≤3 / L1 增量）**缺一则超标到 9–11ms**。
- **作者**：程基岩 | **日期**：2026-09-07
- **关联**：art-bible §3（渲染架构、性能重估、降级方案）、§2④/§2⑤（禁 `shadowBlur`、墨晕预渲染）、GDD① §4.7（三态/四态单一函数）、§4.8（HUD 走 DOM）。

---

## 上下文（Context）

迷雾（关 9+ / 每日）使"静态层全烘焙"假设失效：视野随玩家移动逐格变化，每帧绘制量随视野半径增长。art-bible §3 性能重估给出硬结论：

- 关 9+ 迷雾（R=3，**含 tile 预渲染**）：5–6ms ✓
- 关 9+ 迷雾（R=3，**无 tile 预渲染**）：9–11ms ✗
- R=5（81 格）：8–9ms ✗ 明确超标
- 关 1–8 全烘焙：<3ms ✓ 充裕

即 **tile 预渲染、R≤3、L1 增量更新三者缺一，关 9+ 即 9–11ms，超标**。这是本作性能门禁的硬边界，不可妥协。

## 决策（Decision）

1. **离屏三层**（art-bible §3）：
   - L0 纸底层：纸面 + 极淡网格，烘焙一次，永不失效。
   - L1 记忆层：状态 B/C（记忆态墙 + 已探索通道 + 网格 + 铅笔笔迹），**增量更新**（跨格仅重绘 `dirtyCells`）。
   - L2 动态层：状态 A（视野内墙/通道/实体/玩家/特效），每帧仅视野内 ~29 格。
2. **双渲染路径**（`render/pipeline.ts` 按 `level.visionMode` 切换，**非按来源**）：
   - `'full'`（关 1–8）：L1 为空，回退全烘焙——L0+L2 合并为单张静态层，每帧一次 `drawImage` + 实体叠加（<3ms）。
   - `'fog'`（关 9+ / 每日）：走三层增量（5–6ms）。
3. **三必做前置声明为不可省略项**（若实测缺失则等于超标）：
   - 墙/门/笔迹三类图案**预渲染为 40×40 tile 精灵**（`render/tiles.ts`）。
   - 视野半径 **R=3**（切比雪夫，约 29–30 格），全局恒定（D12 纯半径、不做 Bresenham；**已裁决**：art-bible v2 自解 Q1/Q4，原「R=4~5 渐进」方案作废，改「关卡复杂度渐进 + R 恒定 3」）。
   - L1 记忆层**增量更新**，禁止跨格瞬间全量重烘焙。
4. **禁 `shadowBlur`**；墨晕用启动期预渲染精灵 `drawImage` 替代（art-bible §2④/§2⑤）。
5. **HUD 走 DOM**（顶部 32px，`aria-live`），不占迷宫区高度（守住 A6 一屏一关）。
6. **视野重算时机**：玩家逐格移动，视野只在跨格时变（最快 ~8 次/秒），增量更新即可，非每帧。
7. **降级预案**（实测仍超按时按序启用，art-bible §3）：① 关 9+ 粒子 60→30；② 常驻动效降频（出口脉冲 2.0s→3.0s）；③ 墨晕仅用于钥匙/出口；④ L2 半分辨率离屏放大。

## 后果（Consequences）

**正面**：关 1–8 性能充裕（<3ms），关 9+ 达标且有小余量（5–6ms）；三层离屏 + 增量天然适配 `visited` 单调增长（记忆层随探索增量绘制，永不全量）。

**负面 / 约束**：
- 渲染层需维护 `dirtyCells` 脏区集合与 L1 离屏 canvas，复杂度高于单画布直绘。
- R **上限锁死为 3**（已裁决：不得改大，否则突破关 9+ <8ms 预算），迷雾"渐进引入"只能靠**关卡复杂度**（关 9–10 用小迷宫 + 简单拓扑），不能靠调大 R（Q4 已落）。原 R=4~5 渐进方案作废，无被推翻风险。**缩小 R（如 3→2）不在禁止范围**——仅降低绘制量，更省。
- 若实测关 9+ 触及 7.5ms+，须立即启用降级预案，不得静默放过。
- **「关闭迷雾」是唯一允许的渲染代码分支**（可访问性 Standard/Comprehensive）：覆盖 `cellRenderState` 返回值（经 `AccessibilityMode` 参数）、复用关 1–8 全烘焙路径、不改变 `visible`/`visited` 集合；架构已在 `render/draw-cell.ts` 预留挂载点（详见 main-architecture.md §7）。

## 验收口径（Acceptance）

| # | 判据 | 方法 |
|---|---|---|
| 性能 < 8ms | 1920×1280 实际像素、13×13、关 9+ 每帧绘制耗时 < 8ms | 帧耗时埋点 / DevTools Performance，连续 1000 帧 P95 < 8ms |
| 三前置存在 | tile 预渲染 / R≤3 / L1 增量 均已实现且不可由配置关闭 | 代码审查 + 控制清单勾选（见 `control-checklist.md`） |
| V6 | 三态/四态与 visionMode 严格对应 | 关 1–8 任意帧不出现 UNKNOWN/MEMORY_WALKED；关 9+ 可达两态 |
| V8 | HUD 不迫使滚动 | 1080p 下 13×13(520) + 32px HUD ≤ 592px 可用高度 |

**可自动化项**：`metrics.ts` 中 `VISION_R` 必须 **≤ 3**（当前值 **2**，单元断言；见文末 2026-09-09 修订记录）；`render/tiles.ts` 必须存在且被 `pipeline.ts` 引用（导入图检查）；性能埋点 CI 阈值 < 8ms。

## 修订记录（2026-09-09）

- **修订项**：视野半径常量 `VISION_R` 由 **3 改为 2**（`src/core/constants/metrics.ts`）。
- **理由**：玩家浏览器试玩反馈「难度偏简单」。R=3 下玩家几乎能一眼看清整片局部，探索与记忆负担低；缩到 R=2（切比雪夫，视野内约 25 格）后，对路径、钥匙与门的空间记忆要求明显上升，难度提升符合预期，且仍属关卡复杂度渐进的一部分。
- **是否违反本 ADR**：**否**。本 ADR 的硬约束是「R 不得改『大』（4/5，会突破关 9+ <8ms 预算）」，缩小 R 不在禁止范围。本 ADR 决策第 3 条原写为「R=3」属当时落点，实质是「R 上限 = 3」；本次仅下调当前值，未触碰上限，故不构成推翻。
- **性能影响**：R=2 比 R=3 视野内格数更少（约 25 vs 约 49），每帧 L2 动态层绘制量下降，**理论上更省，不会突破 <8ms 预算**（性能实测数字尚未复测，待浏览器帧耗时埋点复核；即便持平也仍在预算内）。
- **联动改动**：CI 闸门 `tests/ci-gates/vision-r-constant.test.ts` 断言由 `=== 3` 改为 `=== 2`；`metrics.ts` 顶部注释与本文决策/后果同步修正「上限 R≤3」措辞。星级判定、锁深、选关逻辑均不受影响。
